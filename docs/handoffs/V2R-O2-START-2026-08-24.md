## 3. 管理者预检发现的必修缺陷

以下不是建议项，必须先写失败测试再修：

1. `DAG_STEPS` 与验收合同不一致，缺少显式“释放可卖、风险/损益、对账”等阶段；当前还没有生产 EOD factory 将真实服务按合同接线。
2. `SchedulerRunner` 根本没有获取/续租/释放 lease，并发 runner 可同时进入业务步骤。
3. `acquire_lease` 的 SELECT→UPSERT 不在 `BEGIN IMMEDIATE` 原子事务中，存在并发抢占竞态。
4. `step_attempt_status` 只读取 SUCCESS；进程重启后失败 attempt 会从 1 重新计数，可无限越过 `max_attempts`。
5. 同日重放必须按账户/交易日/输入身份幂等；不得重复成交、现金、持仓批次、信号 observation/outcome、草稿或业务审计。
6. 上游失败必须阻断全部下游，特别是估值失败后不得对账为通过、对账失败后不得生成草稿或 COMPLETE manifest。
7. `record_audit_event` 声称幂等但事件 ID 包含当前时点，同一 correlation/action/request 实际会重复写；并发 SELECT head 后 INSERT 还可能形成分叉链。
8. `AUDIT_SIGNING_KEY` 是源码硬编码常量，签名不具备可信隔离。改为调用方注入或受忽略环境变量，缺失时明确 `INSUFFICIENT/ERROR`，测试显式注入固定测试 key；日志、报告和数据库不得出现 key。
9. 告警 payload/error 需要与审计相同的递归脱敏，禁止 Token、密码、API key 或完整账户号进入持久记录。
10. `soak_monitor_v2.py` 目前只看 manifest COMPLETE，可能把 DAG 失败或仅纸面 cycle 当成有效 soak；有效日必须至少同时具有匹配的 `dag_runs=COMPLETED` 和不可变 COMPLETE manifest，并披露对账/审计身份。重复收集同一天不得增加天数。

## 4. 冻结 EOD 顺序

主业务顺序必须显式可断言：

1. 交易日、数据新鲜度和未处理公司行为门禁；
2. 释放到期可卖批次；
3. 撮合此前确认订单；
4. 收盘估值；
5. 风险与损益快照；
6. 内部对账；
7. 信号 outcome 回填；
8. 读取当日信号并生成下一交易日草稿；
9. 固化 daily manifest。

租约、审计、告警和备份校验属于包围控制，不得插入后改变上述业务因果顺序。每个步骤都必须有显式依赖；不能靠列表位置和约定俗成。

## 5. TDD 与验收场景

先提交 RED 证据，再最小实现。至少覆盖：

- 固定 DAG 顺序与每个依赖边；
- 同账户/交易日两个并发 runner，只有一个获得租约并产生成功 run；
- 同 holder 续租、其他 holder 未过期拒绝、过期后可接管、退出释放；
- 第 1/2 次失败和第 3 次终止在重启后仍保留 attempt，第四次不得执行；
- 同输入完整重放，成交/现金/持仓/信号/草稿行数和余额不变；
- 输入身份变化不得复用旧成功步骤；
- 同步失败、行情缺失、公司行为未处理、撮合中断、对账一分钱差异、审计写失败、进程重启七类故障注入；
- 每类上游失败的下游阻断和结构化错误；
- 审计相同请求幂等、并发链不分叉、篡改可检测、缺 key 拒绝签名、敏感字段不落盘；
- 告警去重、脱敏、GET/只读查询零写入；
- soak 只计不同真实 COMPLETE 交易日；DAG FAILED、manifest 缺失、日期伪造、仅 `pt_cycle` 均不计数；
- Windows 进程重启/连接中断后数据库不遗留永久 RUNNING 或永久 lease。

必须在 `pyproject.toml` 注册 marker，并证明实际收集到用例：

```powershell
& $py -m pytest -m fault_injection --collect-only -q
& $py -m pytest -m fault_injection -q
```
